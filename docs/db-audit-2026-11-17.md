# Database audit (task 29.1), 2026-11-17

A report for the owner: what is fine in the schema, what to fix and in what order. The facts were collected by a script from the models
(`src/models/`) and from the local development database (PostgreSQL 16.15, 43 tables, 278 MB). Volumes on the production server
will differ, but the conclusions about the structure do not depend on them.

## In brief

The schema is in good shape: there are no discrepancies between the models and the database, natural keys are protected, and the main queries
use indexes. No gross errors that could lose or corrupt data were found. Six
redundant indexes (fixed in this same PR), one slow lookup (fixed) and several data-design decisions that
are better made before growth were found — they are described below and need your choice.

## What is fine

- **Models and database match.** `alembic check` finds no differences; all 57 migrations apply up to the head.
- **Time.** All 61 time columns are timezone-aware (`timestamptz`); there are no naive ones.
- **Natural keys are protected.** 27 uniqueness constraints: a participant's place in a tournament, the "follower —
  player" pair, a puzzle from a source, a repertoire move, a player's achievement, a game in a collection and so on. Where a key
  is composite by meaning (puzzle theme, theme progress, exercise record), it is the primary key.
- **Deletion of related data is well thought out.** Of 58 foreign keys, 43 are `CASCADE` and 10 are `SET NULL`; there is not a single
  `SET NULL` on a required column.
- **The main queries use indexes:** a player's game archive, position lookup in the opening reference, notifications,
  puzzle attempts, games of a collection.
- **No orphans:** no themes without puzzles, positions without games, or games without players were found in the database.

## Fixed in this PR

1. **Six redundant indexes: the database shrank from 278.3 to 249.9 MB.** Four duplicated the primary key (`ix_games_id`, `ix_users_id`,
   `ix_moves_id`, `ix_bot_personalities_id`), two duplicated the start of the unique index in the position index
   (`ix_position_games_position_hash` — 15.9 MB, `ix_position_stats_position_hash` — 11.1 MB). Each redundant
   index slows down writes and takes up memory; after removal the queries go through the primary key and the unique
   index; plans were captured before and after, the cost is the same.
2. **Case-insensitive player lookup by name.** Profile, registration, player search and reports look up by
   `lower(username)`, and there was no index for that expression — every query read the whole players table. Added
   the index `ix_users_username_lower`: the estimated query cost dropped from 355 to 77.

## Findings awaiting your decision

### 1. The position index is 65% of the database (priority: medium, before growth)

`position_games` and `position_stats` take 180 MB of 278 with 27.6 thousand games: there are 30 rows per game.
At 1 million games that is about 6.5 GB and 30 million rows.

- Both tables have a surrogate primary key `id` that nobody uses (0 accesses) — another 27 MB. Make the pair
  (`position_hash`, `game_id`) and (`position_hash`, `move_uci`) the primary key: this is a key change, a separate
  migration.
- Decide which games to index: currently all finished ones, the first 30 plies. For the opening reference,
  games of weak players and blitz can be left out.
- As it grows — partition `position_games` by hash.

### 2. Four representations of a game (priority: medium, this is task 29.2)

A game is stored in four places with different fields: `games` (own games, the masters' archive, tournament simulations),
`library_games` (the library), `imported_games` (from other sites), plus `moves` — a moves table that is almost
empty: 75 rows for 4 games out of 27,627; the moves actually live in the PGN.

- Decide the fate of `moves`: either delete it (moves are in the PGN, analysis in `analysis_json`), or always populate it.
  A half-way state is worse than either option.
- Archive players (4,531 records) live in `users` together with real accounts: they have no `username_key`, and every
  "real players" query has to filter them out. Move them to a separate `archive_players` table, or at least
  add a partial index over real players.

### 3. Enumeration values without a database check (priority: low)

24 columns store one of several values as a string (`tournaments.status`, `reports.kind`, `feedback.status`,
game results), and there is one `CHECK` constraint in the database for the whole schema. Currently correctness rests on the code. An error in the
code or a manual edit can write a nonexistent status. Adding `CHECK` on statuses and results is a mechanical
migration that does not change behavior.

### 4. Foreign keys without an index (priority: low)

14 reference columns without an index. While the tables are small, this is not noticeable. As they grow, deleting a player will read
`arena_games` in full (two columns with `CASCADE`), `games.winner_id`, `moves.player_id`. Add indexes wherever a reference
takes part in a cascade or a selection.

### 5. Deleting a player and their games (priority: low, verify the intent)

`games.white_player_id`, `games.black_player_id`, `games.winner_id`, `moves.game_id` and `moves.player_id` have no
delete rule set: the database will not let you delete a player who has games. Currently this does not get in the way, because an account is anonymized
rather than deleted. It is worth recording this as a decision right in the models (`RESTRICT`), so that it does not look like an omission.

### 6. JSON in text columns (priority: low)

`games.analysis_json`, `imported_games.analysis_json`, `bot_personalities.config_json`,
`tournament_players.config_json` are text; elsewhere the `JSON` type is used, nowhere `JSONB`. As long as nobody searches by contents,
there is no difference. If queries over the analysis are needed (for example, "games with a blunder on move 20"), switch to
`JSONB`.

### 7. Indexes that are not used (priority: low, re-check on production data)

`ix_games_eco`, `ix_games_site`, `ix_users_is_cheater` — 0 accesses in the local statistics. The local database is not
representative: decide from the production server's statistics a month after launch.

## What was not checked

- Load: the plans were captured on local volumes. At a million games some of the plans will change — re-check after
  the archive is loaded onto the server.
- Backups and restore: the `backup` service exists, but a restore check was not part of this audit
  (recorded in 29.2).
- Redis: the state of games in progress and of queues is a separate topic and is not part of the schema audit.

## Done by the owner's decision (18.11)

Finding 1, first part — migration `c9a4e7d2f5b8` (`chore/position-index-keys`): `position_stats` has the primary key
(`position_hash`, `move_uci`), `position_games` has (`position_hash`, `game_id`); the surrogate `id` columns and the unique indexes that
duplicated them were removed. Not done: selection of the games to index (weak players, blitz) and partitioning — to be decided from
the production server's statistics.

Findings 3–5 were closed by migration `59c61fc287c2` (`chore/db-integrity`):

- **Indexes** on all 15 references without an index (`invites.created_by` and
  `hidden_conversations.other_id` were added to the 14 from the report; `games.winner_id` and `moves.player_id` are among them).
- **Explicit `RESTRICT`** on `games.white_player_id / black_player_id / winner_id` and `moves.game_id / player_id`.
- **`CHECK` on 20 enumeration columns.** The value sets are tuples in the models (`src/models/base.one_of`); their
  agreement with the service checks is verified by `tests/test_db_integrity.py`. The migration first looks for invalid
  values and stops with a list of them; the local data passed the check.
- **Deliberately without `CHECK`:**
  - `games.status` — already a dedicated PostgreSQL enum type;
  - ~~`games.result` and `imported_games.result`~~ — closed by migration `f2a7c4e9b1d6`: the result of a foreign PGN is normalized
    by `game_engine.normalize_result` (import, library, archive loader), the stored strings were normalized, and the `CHECK`
    was added;
  - `puzzles.source`, `defense_drills.source`, `notifications.kind`, `product_events.kind`,
    `tournaments.career_stage`, `games.termination` — registries that grow with data.

## Proposed order

1. A decision on the `moves` table and on archive players in `users` (finding 2) — the rest depends on it.
2. Composite primary keys in the position index (finding 1).
3. `CHECK` on enumerations and indexes on foreign keys (findings 3 and 4) — in one migration.
4. The rest — by the production server's statistics.
